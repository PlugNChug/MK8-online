## 5. E2 and acquire-bound A/B — not run

- **There is no `MK8_E2` switch.** The E2 work is instrumentation only and is always compiled in
  (`toolchain/submit_profile.py`): `[present] flush`/`[present] lock, call` above 5 ms, `[submit] pre` above 50 ms,
  `[acquire]` above 5 ms. `LARECOMP_VK_PROF=1` only adds per-submit detail. An E2 "on/off" A/B therefore needs a
  rebuilt binary without the patch, not an environment switch; that comparison was not made.
- Measured `[present]` lines under load are meaningless (e.g. `[hitch] frame 96 … present 1895.8`), so none are
  reported as results.
- **Acquire bound** (`MK8_ACQUIRE_MS`, default 100, `0` = `UINT64_MAX`) and **occlusion stale** (§7) are the two
  switches that would make a clean ABBA possible; both need `load < 2`.

## 6. Reverse engineering of the remaining stall classes (read-only)

Method: the module was decompressed to a flat ELF for analysis only (`/tmp`, not committed), NVN strings and
ADRP+ADD/LDR pairs were scanned, and call sites were mapped to the recompiler's function boundaries
(`generated/<mod>/…`, `f_<address>`). Guest addresses are MK8 4.0.1 AArch64; no guest code was modified.

### 6.1 How NVN is bound (context for every GPU wait)

The game resolves NVN entry points by name once at startup, storing each host stub pointer in a table of pointers at
`0x700130b000`. The name table and the stores are in the function containing `0x7000585ae4`:

| NVN entry | name address | slot global |
|---|---|---|
| `nvnCommandBufferReportCounter` | `0x7000ef58ff` | `0x700130b000 + 0x3e0` |
| `nvnCommandBufferResetCounter` | `0x7000ef591d` | `0x700130b000 + 0x3e8` |
| `nvnCommandBufferSetRenderEnable` | `0x7000ef5956` | `0x700130b000 + 0x3f8` |
| `nvnCommandBufferSetRenderEnableConditional` | `0x7000ef5976` | `0x700130b000 + 0x400` |

### 6.2 Conditional-sample waits (Y4)

`SetRenderEnableConditional` call sites (7, all in `main`):

| function | offset | second site |
|---|---|---|
| `f_70006a0d50` (small wrapper) | `+0x88` | — |
| `f_70006e8210` | `+0x1a4` | `SetRenderEnable` at `+0x1e0` |
| `f_70006e846c` | `+0x190`, `+0x304` | `+0x1d0`, `+0x340` |
| `f_70006e8840` | `+0x180` | `+0x1c0` |
| `f_70006e8ab4` | `+0x188`, `+0x2e8` | `+0x1c8`, `+0x32c` |

The reports those conditions compare come from **`f_7000aed30c`**, a per-scene-entry loop:

- `+0xc0` `nvnCommandBufferResetCounter`, guarded by `tbz w20, 0` (`+0xbc`),
- `+0x264` `nvnCommandBufferReportCounter(type=1 = SAMPLES_PASSED)` with
  `x2 = x0 + (byte[x23+8] << 5)` — the counter slot advances per entry, inside the loop at `+0x228`…`+0x270`.

`f_7000a8482c+0xb0` is the other `ReportCounter` site and passes **type 0x10**, not 1 (frame timing). So the
occlusion path is a per-entry loop: reset, report samples, later draw with a conditional enable that must read those
counters.

**Why the wait exists:** the host resolves occlusion queries only when the producing submission retires
(`mk8_oq_resolve_done` in `toolchain/occlusion.py`), so replaying the conditional enable while that submission is
still pending in `vkWaitSeq`-blocks the render thread. That is the 1,617 waits / 973 ms / worst 114 ms class.
The failed mitigation (submitting at report end) traded the wait for +6,400 submits; the untried direction is the
opposite: read the last resolved value and accept one submission of staleness (§7).

**Testable hypothesis:** with the counters one submission stale, object visibility decisions change by at most one
frame; the total wait should drop to ~0 without extra submits. Verify by counters (`waits:` line), screenshots at the
same frames as the baseline, and the same draw/skip counts (the only expected change is a few culled/unculled
objects at the transition).

### 6.3 Core waits (C1)

`[slow]` lines (this turn's diagnostic run, `LARECOMP_PROF_SVC=1`) give the guest return address of every long svc.
Aggregated by (thread, svc, LR), with the caveat that the host was at load ~60 so the milliseconds are inflated:

| tid | svc | n | total ms | max ms | guest LR (module) |
|---|---|---|---|---|---|
| 103 | `0x34` WaitForAddress | 272 | 28,370 | 204 | `0x700408d9f8` (sdk `f_700408d930+0xc8`) |
| 107 | `0x18` WaitSynchronization | 1,364 | 27,372 | 941 | `0x7004096678` (sdk `f_70040965ec+0x8c`) |
| 80 | `0x1a` ArbitrateLock | 9 | 5,118 | 1,865 | `0x7004096f2c` (sdk `f_7004096ee8+0x44`) |
| 96 | `0x21` SendSyncRequest | 2 | 1,694 | 1,676 | `0x70040a0154` (sdk `f_70040a0120+0x34`) |
| 80 | `0x34` | 3,833 | 1,505 | 29 | `0x700408dad8` (same futex wrapper) |

Raw wait conditions, unmodified:

```
[slow] t103 svc34 204ms a=728396bb08,2,1,bebbf8f h0=0 lr=700408d9f8
[slow] t107 svc18 941ms a=7229ee5ec8,7229ee5ecc,1,5f5dcba h0=137 lr=7004096678
[slow] t80  svc1a 1865ms a=10e,7253413130,101,f4037 h0=0 lr=7004096f2c
[slow] t96  svc21 1676ms a=10b,7090002000,10b,0 h0=0 lr=70040a0154
```

- The `0x34` waits are a **futex timeout** (timeout argument `0xbebbf8f` ns ≈ 200 ms) that recurs 272 times on the
  same address `0x728396bb08` — a wait that is never woken, not a lost wake-up.
- The `0x18` wait is on handle `0x137` (one handle at `0x7229ee5ec8`, timeout ≈ 100 ms); 941 ms is contention on an
  event/mutex (thread 107 is a loader/worker), not the timeout.
- The `0x1a` wait is a **guest mutex at `0x7253413130`** (handle `0x10e`, tag `0x101`), main thread, up to 1.8 s;
  `toolchain/core_preempt.py` hands a core over only to a waiter of *better* priority (`w->prio < owner->prio`), so
  equal-priority contention still runs to the holder's next kernel call — this is the C1 remainder, not a missing
  yield.
- The `0x21` wait is an IPC round trip on session handle `0x10b` (message at `0x7090000000`), 1,676 ms on thread 96
  and 504 ms on the main thread at boot.

**Concrete hypothesis for the 901 ms boot stall:** it is not rendering. The recorded hitch is
`frame 3: 901 ms = backend exec 0.6 + prefetch 0.0 + present 1.7 + other 898.5; 5 draws, 2 submits` — 898.5 ms in
"other", i.e. the guest produced no frames. The IPC evidence above (a single 1.68 s `SendSyncRequest` at boot on
handle `0x10b`) is the same order and the only guest-side wait that long in the boot window. A run with
`LARECOMP_PROF_SVC=1` (already implemented, no code change) on a quiet host will confirm or refute it by the LR of
the boot-window `0x21` call.

### 6.4 Track loads (114/156 ms)

`frame 2109: 114 ms = exec 0.2 + other 112.7` — again "other": no GPU work in the frame; the guest is between frames
(RomFS read + Yaz0 + asset setup). `frame 2137: 156 ms = exec 87.1 (GPU waits 21.5) + prefetch 39.1 + present 1.1 +
other 28.4; 3,282 draws` — this one is the first-use path: translation on the render thread (prefetch 39 ms) and
first-use uploads inside exec. The Yaz0 share is now small (native path); the remaining cost is texture creation and
first-use uploads, matching STATUS.md's "2,221 image views / 91.6 MB".

### 6.5 Prefetch scans (H1)

Across 826 race-window `[shader] prefetch` windows in `local/qualification/*.log` (excluding cold-cache logs with
multi-second scans): **median 132.75 ms, p95 513.3 ms, max 860.3 ms** per 600 frames. Cold logs reach 7–88 s
(`coldguard.log`, `coldwarm.log`), which is first-use translation, not steady state. This build's own diagnostic run
(menus, load ~100) scanned 76.3–171.2 ms per 600 frames — consistent with the distribution, not a measurement. The
scan runs on the render thread and translates inline; that is the measured cost, and the audit's 4-worker proposal is
the mitigation blocked by two globals (`maxwell_gmem_base/size`).

## 7. Experiments

### 7.1 Implemented (default off): `MK8_OCCL_STALE`

`toolchain/occlusion.py`: when a conditional render enable still has a pending report, keep the value the last
completed submission wrote instead of flushing/waiting:

```c
static int mk8_oq_stale = -1;  // MK8_OCCL_STALE=1 (experiment, default off)
...
if (mk8_oq_stale < 0) mk8_oq_stale = getenv("MK8_OCCL_STALE") != NULL;
if (mk8_oq_stale) return;
```

Default stays byte-identical to the current behaviour (the gate is off). Not validated: the host never allowed a
controlled run, and this is exactly the kind of visibility change that needs screenshots and draw/skip counts on a
quiet machine. Expected: `waits:` conditional-sample count → ~0, submits unchanged, at most a one-frame visibility
difference. The right first check is `MK8_OCCL_STALE=1` vs off on the same frames, comparing the `waits:` field and
`drawn/skipped` counts, then the recorded screenshots.

Test: extended `tests/test_occlusion.py` (same native harness) with a pending report and `mk8_oq_stale=1` asserting
no flush, no wait and the previous counter values kept. The suite's own invocation is zig's
`cc -target x86_64-windows-gnu` (Windows/CI); on this Linux host the same harness was compiled with a wrapper that
drops those two arguments: **the test passes**, and a negative control with the gate disabled
(`if (0) return;`) **fails**, so the case exercises the gate rather than the text. The patch also compiles in the
real host build (`--runtime-only`, exit 0). Runtime smoke test with `MK8_OCCL_STALE=1`: boot and title/menu frames
200–300 rendered, exit 0, but **0 conditional-sample windows**, so the changed path was not reached; race validation
is still required (host busy).

### 7.2 Proposed (not implemented): guest PC sampler for long frames

The 901 ms boot and the 114 ms load both sit in the frame's "other" bucket with almost no GPU work, so the current
hitch line cannot name the guest function. Proposal: behind `MK8_FRAME_PC=1` (default off), when a frame exceeds
100 ms, sample the running guest thread's `c->pc` at ~1 kHz into a small hash table and log the top 5 functions with
sample counts at frame end (same `vk_prof_frame` hook that prints `[hitch]`). Cost is bounded by the hitch rate; the
table is 4 KiB. Test plan: extract the histogram update (address → bucket, top-N) into a function and drive it with a
synthetic sequence in a native test, then validate attribution against `LARECOMP_PROF_SVC` on the same boot.
This is measurement only (no behaviour change), and it is the prerequisite for the boot/load work the audit ranks
first.

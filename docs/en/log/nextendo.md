## Steam and Nextendo account refusals in the 0.5.0 test build

The launcher tries the configured DLL, the data folder and the executable folder before querying the game libraries. A local DLL that initializes the required interfaces makes the scan unnecessary. If the interfaces fail, the next candidate is tested.

When Nextendo ends the session with code 2 because of an account refusal, the launcher uses the log of that run to show the guidance in the warning and on the Play screen. The messages include Discord linking, email verification, a disabled account and a session on another device. Other valid codes appear as reported by the service. Fatal runtime failures keep priority in the diagnosis.

On Windows, the local setup reports 0.5.0 in the executable metadata, in the API and in the interface. It recognized data prepared on 0.4.1 and offered the update. The isolated runtime swap installed the executable contained in the package and preserved the hashes of the four game DLLs. With a test DLL lacking the Steam interfaces in the data folder, the launcher API listed the friends using the copy installed with Cuphead. In the packaged game and launcher, a test Nextendo service on loopback answered `discord_unlinked`. The warning, the guidance on the Play screen and the diagnostic ZIP were verified. When the service released the account, a new attempt reused the authorization, reached the title screen and cleared the previous message. The public race test between PCs remains separate.

On 0.5.0, 109 Rust tests and 35 browser tests of the launcher and installer passed, including the local relay. Formatting and Clippy passed. The optional Rust test that creates a real Steam room remained pending. The test setup has SHA-256 `433d5ff7173ec6e68d4cf01afa47adc186d2a938a6545e72effa4829a88430fe`.

## Initial Nextendo investigation — before the prototype above

Feasibility: there is a technical basis for an MK8 Deluxe 4.0.1 prototype, but there is no qualified Nextendo login, matchmaking or race in this build. The site declares MK8 support; the consulted notes of Ryujinx-Nextendo 1.9.7 require exactly 4.0.1. This matches the project's supported profile, without proving interoperability. Some of the GitHub links returned 404; the current portal points to Forgejo at `git.nextendo.network`. References in THIRD_PARTY.md.

Local inventory, read-only: `upstream/smm2recomp/recomp/runtime/net/nextendo.c` contains OAuth Authorization Code + PKCE, loopback callback, renewal and obtaining a game token; `netcfg.c` contains routing/DNS and TLS with a pin; `services/acc.c` injects identity/token into the account service. There are `bsd_host.c`, `ssl.c` and `nifm.c`. `toolchain/host.py` compiles the generic sources of `runtime/net`, so inherited client code exists, although there is no activated/qualified MK8 integration. The network configuration hooks remain the defaults of `game_hooks.c`; `friend.c` provides empty/offline lists. The current LAN/relay bridge is a separate transport and does not replace NEX/Pia authentication.

Points to resolve before activating:

- Register a MK8-online application of its own in the developer portal, confirm matchmaking permission for MK8, redirects, scopes and any approval/attestation required for an independent client. The portal offers a public PKCE application; the fork's README also describes attestation of official builds. Do not assume that the contract of one client is that of the other. Do not reuse the embedded SMM2 CLIENT_ID or extract keys from official builds.
- Confirm with the current documentation the endpoints, application/title identity, exact version, BAAS/NEX token, routes and TLS trust. The IPs and the pin in upstream record an October observation and were not validated against production in this investigation. Simply pointing our relay at Nextendo is not enough.
- The base's `secure_store.c` writes tokens to `net/nextendo.txt` on Windows; use per-user protected storage, separate from saves/reports. `nextendo.c` uses a `rand()/time()` fallback if entropy is missing: fail explicitly in that case. Coordinate token renewal/rotation between instances; logout must not delete profiles or saves.
- Adapt the services and states that MK8 4.0.1's own NEX client requests; trace real failures of account, BSD/DNS, TLS, matchmaking and Pia/NAT. Do not return fictitious success to get through menus. Friends/presence require additional implementation; do not present empty lists as an integrated service.
- Preserve licenses: the Nextendo fork's additions and the documentation/servers declare PolyForm Shield; the MIT license inherited from Ryujinx does not automatically cover those additions. Do not incorporate that code into the GPL project without clarifying rights/compatibility. Prefer our own protocol adapter, with references and tests of its own.

Recommended sequence: (1) application/contract and local lab; (2) login through the browser, logout and renewal with protected storage; (3) local account/DNS/TLS/NEX test and diagnosis of the online menu in MK8; (4) authorized private Nextendo lobby between two clients; (5) full race, result, restart and save on two machines/networks; (6) interoperability with a supported Nextendo client, reconnection/NAT and friends. Leave cloud save synchronization out of the first prototype. Future changes stay in launcher, runtime/mk8 and toolchain; upstream remains intact.

In this round no accounts/applications were created, no messages were sent to the maintainers, no tokens were used, no matchmaking was triggered and the runtime was not changed. The public pages and local sources support the analysis; there was no online test. `gameplay_verified` remains false.

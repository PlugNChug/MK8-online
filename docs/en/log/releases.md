## Setup 0.4.0 on an exFAT SSD — “Can't restore time: Invalid argument”

One report (Windows 11 25H2, fresh install, data folder at `G:\...` on an external exFAT SSD) stopped at 81%, at **Prepare launcher files**, with `Can't restore time: Invalid argument` for every payload file. The payload is written with `ZipInfo(name)`, which uses the default ZIP date: 1980-01-01 00:00 in local time. Extracted without `-m`, Windows `tar.exe` restores that date; here (UTC−3) the file ended up with 1980-01-01 00:00 local. East of UTC, this corresponds to 1979-12-31 in UTC, below the exFAT minimum, and `SetFileTime` fails. On NTFS, the same date is accepted. The setup now extracts with `tar -xmf` (`extract_payload`), keeping the extraction date.

An exFAT disk would have failed next: the build exposes the RomFS through hard links (`mirror`), and FAT32/exFAT do not support them. The message said “must be on the same disk”, even though it was the same disk. The setup now queries the volume's `FILE_SUPPORTS_HARD_LINKS` (`GetVolumeInformationW`), shows the warning when the data folder is chosen and refuses installation on that disk. The build reports that the disk does not support hard links and must be NTFS. A full copy was not made as an alternative, because that would duplicate about 11 GB.

Validation: the Rust test `payload_extraction_does_not_restore_the_1980_zip_date` extracts a ZIP with the 1980 date through the real helper; without `-m`, `tar` restores 1980, as checked manually. Also passing: the file-system refusal test (real NTFS; exFAT by the rule), the browser test of the warning in English and Spanish, the `mirror` test with WinError 1, 104 Rust tests of the workspace, Clippy and formatting. This machine has no exFAT volume, and creating one requires administrator rights, so the setup has not yet been run on a real exFAT disk.

## Tool updates and uninstall on Windows

On `fix-chore`, a previous build already on disk could unlock the rebuild step even with missing tools. The launcher now opens on Tools in that case. After verification, it proceeds to Build if the inputs are ready or to Game files if any is missing. The backend also checks the prerequisites before starting the build.

The update cleanup recognizes the packages extracted by the launcher and removes obsolete Python environments and private copies of tools. To remove a replaced shared Zig compiler, it checks the previous version and the executable hash recorded at installation. The cleanup stays out of the save and build directories.

The setup installs `Uninstall.exe` next to the launcher and registers that executable in Windows Installed Apps. The default mode preserves the data folder for reinstallation. The full mode requires confirmation, checks the game and build locks and refuses trees with junctions. In preexisting data folders without an ownership marker, it removes only items recognized as MK8-online.

The native test in test folders on C: and D: updated version 0.3.0, canceled an uninstall, removed the launcher while preserving a save, reinstalled and ran the full removal. A file next to the data folder survived both options. The test restored the previous installation registry entry and shortcut.

## Relocation of the Windows portable package

The operation uses preparation and build locks, validates JSON before applying changes, preserves metadata backups and writes the new location last; repeating it after an interruption is idempotent. It only walks known own metadata, without modifying identity saves/profiles, binaries, embedded fonts or game files, and without following links/junctions. External references and an external --data-dir are not migrated. The home/executable paths in pyvenv.cfg follow the bundled CPython. Thin archive files now use relative references to the objects. The --finish flow rebuilds old archives from the verified objects before linking and updates the receipt hash. ## Launcher shutdown and games in other instances — local sources

The executable has two internal supervision modes, triggered before loading the window/payload. Requests go through stdin and confirmation through stdout, without a file holding commands/credentials. The tools/build supervision keeps the locks and watches a handle of the launcher process. Before starting tools, it associates itself with a Windows Job Object with `KILL_ON_JOB_CLOSE`; descendants inherit the job and do not receive its handle. The launcher accepts the base game and the 4.0.1 update of the pinned profile. The pipeline limits reads to the PFS0 container, rebuilds the NCAs compressed as a stream or in blocks and checks the hashes. The LibHac 0.18.0 extractor opens ExeFS, NACP and the combined RomFS with integrity verification. The package includes the helper and its .NET runtime for Windows x64. XCI/XCZ, DLC and other revisions are outside that profile.

The paths of the game and of `prod.keys` stay in the local configuration. The tickets are read from the packages and sent by pipe to the extractor. The final folder only appears after verification and can be reused without keys. The first extraction reserves about 28 GiB free on the launcher's disk and frees the intermediates on completion. Import time is separate from the recompilation time measured with files already extracted.

### Recompilation time

On the Xeon E5-2666 v3 with 16 GB, the run with a fresh directory and empty object and Zig caches published a candidate in **855.6 s (14 min 16 s)**. Tools and extracted files were already available. It took 44.5 s to C generation, 788.0 s to finish the 484 objects and 23.1 s to finalize linking and publish the candidate. The host and the DLL linking preparation ran in parallel with the game compilation. Parallel generation preserved the hashes of the 482 C units. The local log is `local/cold-15-final.log`. The practical planning range for this machine is 20–25 minutes when there are other loads. The measurement verifies preparation, not the speed or stability of the game.

## Build and storage

The host can be updated without recompiling the game modules, using the README command. Changes to ABI, generator or guest patches require the corresponding consumers. Dependency and generated sources are verified; own adaptations are applied to the private copies.

Reuse `native-optimized` and `host-optimized`. The pipeline verifies a minimum reserve of 4 GiB. The user already cleaned the old cache; do not repeat the previously blocked deletion. There is no automatic build collector. Keeping only the test build and one replacement during a validated update is the intended policy; do not delete saves, inputs or junction targets.

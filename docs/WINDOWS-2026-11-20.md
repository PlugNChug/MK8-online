## Static audit of the recent Windows-relevant changes

- `runtime/mk8/graphics/fsr.cpp` and `fsr_bridge.c` are `.cpp`/`.c` under
  `runtime/mk8`, so `toolchain/host.py` includes them in the Windows unit list.
  Both compiled for `x86_64-windows-gnu` in the 222-unit build; a separate
  probe compiled them alone with no warnings.
- `fsr.cpp` uses `#ifdef _WIN32` for `windows.h`, `LoadLibraryA` and
  `GetProcAddress`; the non-Windows branch is `dlfcn.h`/`dlopen`/`dlsym`. It
  does not use `pthread` or POSIX paths. The default provider name is still the
  Linux `libamd_fidelityfx_upscaler_vk.so`; this is only reached when
  `MK8_FSR4` is set, and a failed `LoadLibraryA` returns `VK_NULL_HANDLE`
  without touching the frame. AMD's signed Windows
  `amd_fidelityfx_upscaler_vk.dll` is a separate, explicitly supplied path.
- `toolchain/fsr.py` is text-only preparation (present pass, depth capture,
  device feature query). It has no host-OS branch and ran during the Windows
  host build.
- No FSR setting, toggle or DLL discovery exists in `apps/launcher`; the
  launcher cannot enable the native Linux provider on Windows. The FSR
  feature remains an environment-variable diagnostic, default off.
- `runtime/mk8/graphics/ffx/ffx_api.h` defines `FFX_API_ENTRY` as
  `__declspec(dllexport)`; MinGW/Zig accepts this and the declarations are not
  definitions. No non-Windows construct leaked into the Windows build.
- `scripts/runtime-dlls.py` had two Windows-tooling defects found while
  preparing the build, both fixed in this branch:
  1. MSYS2 packages can ship a DLL as a **hardlink** to another member
     (`zlib1.dll -> libz-1.dll` in `zlib-ng-compat`). Python's `tarfile`
     reports `member.isfile() == False` for the link, so the old code skipped
     it and later raised `DLL ausente no pacote: zlib1.dll`. This would break
     the **Tools** step on a fresh Windows machine, because `avutil`/`swscale`
     import `zlib1.dll`.
  2. `SystemRoot/System32` lookup was case-sensitive when the host filesystem
     is case-sensitive. The no-behaviour-change Windows path still uses the
     exact name; the fallback only applies on a non-Windows host used to
     cross-check.
  The fix was exercised with a synthetic `.tar.zst` containing a hardlink and
  with the full `--prefetch` (104 DLLs verified).

## What remains unverified

- **First frame / gameplay on Windows.** The runtime reaches Vulkan device and
  swapchain creation, NVN window creation and audio device creation, then
  stops at a guest call to `0x7004004c30` from
  `nn::crypto::detail::bigint_mod_mult`. The function is not in the generated
  `sdk` table; `0x7004004c30` is an interior label of the function that starts at
  `0x7004004c10`. This needs a Windows host with a debugger or a recompiler fix;
  it is not a build failure and is not fixed here.
- **Real MSVC release build.** Everything here used the GNU target. A Windows
  machine with MSVC Build Tools, Windows SDK, WebView2 Runtime and .NET 10 is
  still required to reproduce `scripts/release.py`/`package-launcher.py` and
  the WebView2 window.
- **WebView2 window.** The launcher was verified headless (HTTP server and
  embedded page). The native WebView2 window, file pickers, installer and
  update flow were not exercised.
- **Gameplay qualification.** Menu, a complete race, restart/save, image,
  audio, controller and clock speed remain unverified on Windows. The Linux
  control only shows the data is valid.
- **FSR provider on Windows.** AMD's signed Windows DLL was not run in this
  session; only the FFX API path was compiled. The Linux `.so` default means a
  Windows user must set `MK8_FSR_LIB` to the AMD DLL and `MK8_FSR4=1`; the
  launcher does not do either.
- **Package/setup.** `prebuilt/host` and the minimal FFmpeg (`prebuilt/ffmpeg`)
  were not produced; `scripts/build-ffmpeg.py` needs WSL. `scripts/release.py`
  and the 966-file payload audit were not run.
- **Two-PC multiplayer.** Not attempted.
